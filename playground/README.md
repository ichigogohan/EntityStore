# EntityStore Playground — Demo Frontend

`@entity-store` パッケージ(バッチ解決・キャッシュ・楽観的ロックを持つクライアント側エンティティストア)の
挙動を実際の画面操作として確認するためのデモUIです。

## 何のためのツールか

このデモが検証したいのは「大量データを効率よく描画できるか」ではなく、**同じデータへの重複アクセスを
どれだけサーバー・ネットワーク側で削減できるか**です。そのため一覧・タイムラインどちらの画面も、
表示件数そのものより「リクエストの重複がどれだけ減っているか」が見えるように作られています。

## 画面構成

### 1. ユーザー一覧 (`#/`)

- ID空間 `u0000`〜`u4999`(5,000件、`TOTAL_ENTITY_COUNT`で一元管理)を対象にした無限フィード
- 初期表示時に全件はロードせず、下端まで到達するたびに50件ずつ`store.get()`で取得
- DOM上に保持するのは直近200件まで(`FEED_WINDOW_SIZE`)。それを超えて画面外(上方向)に押し出された項目は購読解除してDOMから削除し、削除した高さぶんスクロール位置を補正して見た目のジャンプを防いでいる
- 一度パージされた項目は、スクロールを戻しても再ロードされない(上方向への再取得は未実装)
- 「キャッシュ削除」ボタンで`store.clear()`(非同期)を呼び、フィードごと再構築
- クリックで対象ユーザーの編集画面へ遷移

### 2. プロフィール編集 (`#/profile/:id`)

- 一覧とは異なり`store.getLatest(id)`を使用し、都度サーバーから最新状態を強制取得
- 名前・Bioを編集し`PATCH /profiles/:id`で保存(`version`を送信する楽観的ロック)
  - `409`(バージョン競合)/`410`(削除済み)/`404`(存在しない)/`400`(バリデーションエラー、サーバーのメッセージをそのまま表示)を個別にハンドリング
- `POST /upload`(`X-User-ID`ヘッダー)で画像を送信 → 成功後、タイムスタンプ付きURLを`PATCH`で保存
- アップロード成功・保存失敗という「宙ぶらりん」状態も検知し、再アップロードを促すメッセージを表示
- 削除ボタン(`DELETE /profiles/:id`)。確認ダイアログを挟み、削除後はその場で`status: "deleted"`の
  表示に切り替える(一覧へは自動遷移しない)

### 3. ランダムタイムライン (`#/timeline`)

- ID空間5,000件の中から「ホットプール(200件)」を用意し、8割はホットプールから、2割は完全ランダムにIDを選んでカードを流し続ける無限フィード
- 完全一様ランダムだけだと同じIDの再出現確率がほぼゼロになり、キャッシュヒットが発生する場面をほぼ見せられないため、意図的に偏りを持たせている
- 一覧と同じ`feed.ts`の仕組み(下端検知ロード・画面外パージ)を共有しており、一覧・タイムラインは同じ`EntityStore`インスタンス(=同じキャッシュ)を参照する

### 常設: ネットワーク統計パネル

画面右下に固定表示され、画面遷移をまたいで値を保持し続ける。`/profiles/resolve`への
リクエスト/レスポンスボディを直接覗いて計測しており、ライブラリ内部の実装(メモリキャッシュかIndexedDBか等)には依存しない。

- `requested`: `feed.ts`が`store.get()`を呼んだ回数
- `sent to server`: 実際に`/profiles/resolve`のリクエストボディに含まれていたID数
- `version-matched`: そのうちレスポンスに含まれていなかった(= `clientVersion === serverVersion`で本文が返却されず、キャッシュがそのまま使い回された)ID数
- `cache hit rate`: `version-matched / sent to server` の割合
- `network calls`(参考値): 実際に発生したHTTPリクエスト数(`PerformanceObserver`で計測)。バッチ化により`requested`より大幅に少なくなる

**挙動の注意点**: 起動直後やキャッシュ削除直後はどのIDも「クライアントはバージョンを未知」の状態から始まるため、`cache hit rate`は0%近辺からスタートする。一覧の再訪問やタイムラインのホットプール(同じIDへの再アクセスを意図的に発生させる仕組み)によって同じIDへの問い合わせが繰り返されるにつれて、徐々に上昇していくのが期待される挙動。

## アーキテクチャ上の判断

- **ルーティング**: ビルド設定を増やさず2画面以上を実現するため、ハッシュベースのクライアントサイドルーティング(`#/` / `#/profile/:id` / `#/timeline`)を採用
- **一覧とタイムラインの共通化**: 「下端に到達したら次を読み込み、画面外に出たらパージする」という仕組み自体は同一のため、`feed.ts`に抽象化して共有。両画面の違いは「次にどのIDを読み込むか」を決めるロジック(一覧=連番、タイムライン=ホットプール+ランダム)だけに閉じている
- **一覧と編集で取得経路をあえて分ける**: 一覧・タイムラインは「多数を雑に・速く」表示する場なのでバッチキャッシュ前提の`get()`、編集は「1件を正確に」扱う場なので強制フェッチの`getLatest()`、という役割分担を明示的にコードへ反映している
- **計測はライブラリ非依存**: キャッシュヒット率をライブラリ内部から教えてもらうのではなく、ブラウザの`PerformanceObserver`で実際のネットワークリクエストを客観的に数える方式を採用し、ライブラリの内部実装(メモリキャッシュかIndexedDBか等)に依存しない形にしている

## ファイル構成

```
index.html   … Tailwind CDN + フォント読み込み
app.ts       … 型定義・全画面テンプレート・統計パネルUI
api.ts       … EntityStoreインスタンス・PATCH/DELETE/アイコンアップロードAPI
feed.ts      … 一覧・タイムライン共通の無限フィード(下端検知ロード・画面外パージ)
stats.ts     … ネットワーク計測(延べリクエスト数・実測ネットワークリクエスト数)
main.ts      … ルーティング・画面制御・イベントハンドラ
style.css    … 最小限のカスタムCSS
```

## 技術スタック

- Vite + TypeScript
- Tailwind CSS(CDN版)
- Google Fonts: Inter(本文) / JetBrains Mono(ID・バージョン・統計などの識別子系)
- バックエンド: Fastify + Prisma(別リポジトリ、Vitestでテスト済み)
- アイコン配信: 別ホストの画像アップロード/配信サーバー

## 公開デモとしての制約・前提

- 認証なし。誰でもプロフィールを編集・削除できる想定の、書き換え制限のみのオープンデモ
- 表示側は`escapeHtml`で常時エスケープ済み(XSS対策)
- `iconUrl`が空の場合は`public/Unknown.webp`を参照する

## ローカルでの動作

このリポジトリ単体では動作しません。`EntityStore`パッケージと、`/profiles`系・`/upload`系エンドポイントを提供するAPIサーバーが別途必要です。

```bash
npm install
npm run dev
```
